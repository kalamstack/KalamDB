# KalamDB 0.7 Program

**Status:** Active  
**Target version:** 0.7  
**Date:** 2026-09-01  
**Status date:** 2026-09-06

0.7 is not three independent projects. It is one release whose product bar is: typed nested data that persists and executes correctly, equality lookups that stay prefix scans as tables grow, and SQL-defined server procedures that use those same types.

Implement these three plans together:


| Track                        | Plan                                                                                                                                                         | 0.7 product outcome                                                                                                                                                                                             |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Serialization**            | [2026-02-14-flatbuffers-flexbuffers-vortex-migration-plan.md](2026-02-14-flatbuffers-flexbuffers-vortex-migration-plan.md)                                   | One `kalamdb-serialization` crate. Nested `STRUCT` / `CREATE TYPE` / `List` persist through that crate only. Live USER/SHARED/STREAM row **values** are ordinal KOBJ (identity is not repeated in the payload). |
| **Scalar secondary indexes** | [2026-08-30-scalar-secondary-indexes.md](2026-08-30-scalar-secondary-indexes.md)                                                                             | USER/SHARED scalar `CREATE INDEX`, hot prefix seek, cold bloom/min-max prune, CLI schema-diff, RLS membership bind.                                                                                             |
| **Functions V1**             | [functions-v1-implementation.md](functions-v1-implementation.md) ([design](functions.md), [ADR-021](../architecture/decisions/adr-021-kalamdb-functions.md)) | SQL procedures, generated SDKs, nested typed `CALL`, transactional topics, durable triggers.                                                                                                                    |


Do not ship 0.7 with only one of these. Nested procedure types without a central codec fork persistence. Indexes that keep JSON PK lists fight the serialization migration. Functions that scan `WHERE conversation_id = ?` stay too slow for the chat/RLS workloads 0.7 is supposed to carry.

This file owns **status, remaining tasks, RocksDB value layout, locked keys, and upgrade policy**. Source plans keep design depth (phases, task steps, non-goals). Executable file-level steps: [2026-09-05-kalamdb-0.7-implementation.md](2026-09-05-kalamdb-0.7-implementation.md).

```text
SQL contract (tables, CREATE TYPE, CREATE INDEX, CREATE PROCEDURE)
        │
        ▼
ContractSnapshot / TableDefinition / TypeId
        │
        ├─► kalamdb-serialization     persist STRUCT/List/rows/catalog/index values
        ├─► indexing core             prefix seek + flush prune for equality
        └─► kalamdb-functions         CALL / nested ctx.functions / triggers
                │
                └── uses the same types, same row codec, same indexes
```

Not in 0.7 (stay on the source plans' non-goals): Vortex-as-Parquet, schedules/`CREATE EVENT`, extra function runtimes, unique-by-default scalar indexes, ANN answering scalar equality, changing RocksDB ordered key encoding.

## On-disk / upgrade policy

**0.7 is a breaking on-disk format.** The server will not dual-decode old RocksDB row/object bytes on the hot path.

- No in-process migration of existing cluster data.
- No forever `decode_*_compat` for production reads. Remove FlexBuffers / JSON / MessagePack fallbacks (`decode_object_compat`, `decode_protocol_compat`, `decode_stream_compat`, JSON list fallback) from the server once Wave 4 lands.
- Dev/test clusters: **wipe the data directory**. Old `KENV` / name-keyed rows / unenveloped payloads are not readable by 0.7.
- A **separate offline upgrade tool** (follow-on, not the 0.7 server) will read old codecs and rewrite to the 0.7 layout. Keep old decoders only in that tool. Do not spec the tool’s CLI here.

This matches serialization plan §14 (no silent historical rewrite) but **drops** “detect legacy on every read” for the 0.7 server.

HTTP JSON, WebSocket, PGWire, and SDK payloads stay out of `KOBJ`.

## RocksDB keys (locked)

Serialization plan §9 and §21.2 stay in force: **do not change RocksDB ordered key encoding.** Keep the keys we already use.


| Table  | Logical identity  | On-disk bytes (keep)                                                                                                                      |
| ------ | ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| USER   | `(user_id, _seq)` | storekey tuple via `[UserTableRowId::storage_key](../../backend/crates/kalamdb-commons/src/ids/row_id.rs)`: `encode_key(&(user_id, seq))` |
| STREAM | `(user_id, _seq)` | same storekey tuple as USER (`[StreamTableRowId](../../backend/crates/kalamdb-commons/src/ids/row_id.rs)`)                                |
| SHARED | `_seq`            | `[SeqId::storage_key](../../backend/crates/kalamdb-commons/src/ids/seq_id.rs)` 8-byte big-endian i64                                      |


Prefix scans stay `UserTableRowId::user_prefix` and the existing `StorageKey` helpers in `[storage_key.rs](../../backend/crates/kalamdb-commons/src/storage_key.rs)`.

Keys stay in `kalamdb-commons` (`storekey`). They are **not** FlatBuffers/FlexBuffers and **not** `kalamdb-serialization`. That crate owns **values** only.

Do not compact, re-home, or put `_commit_seq` into the key.

## Optimized RocksDB row values

Today:

- **Key:** as above (unchanged in 0.7).
- **Value:** FlatBuffers `KENV` + name-keyed columns; **duplicates** `user_id`/`_seq` already in the key.

Target value (USER / SHARED / STREAM rows only):

```text
RocksDB key   = existing storekey / SeqId bytes (do not change)
RocksDB value = KOBJ row envelope + compact payload:

  schema_version u16
  commit_seq     u64
  deleted        u8
  ordinal values[]   // schema slots; STRUCT/List recurse; no column names
```

**Drop from value:** `user_id`, `_seq`. Reconstruct them from the existing key on decode.

**Keep in value:** `_commit_seq` and `_deleted` (needed for MVCC/visibility; they are not in the key).

Column names and types live once in catalog / `[StorageSchema](../../backend/crates/kalamdb-serialization/src/row/schema.rs)` (stable physical ordinals, append-only slots — serialization plan §8.3). Nested `STRUCT`/`List` recurse in the same value codec.

### Files to change (Wave 2 serialization)

- Trim identity from `[encode.rs](../../backend/crates/kalamdb-serialization/src/row/encode.rs)` / `[decode.rs](../../backend/crates/kalamdb-serialization/src/row/decode.rs)`. Decode APIs take key identity + schema + bytes.
- `StorageSchema` from `TableDefinition`. Wire `[user_table_store.rs](../../backend/crates/kalamdb-tables/src/user_tables/user_table_store.rs)`, `[shared_table_store.rs](../../backend/crates/kalamdb-tables/src/shared_tables/shared_table_store.rs)`, and providers to pass schema.
- Remove `USES_ROW_CODEC` and model `encode`/`decode` as the live codec. `[persist.rs](../../backend/crates/kalamdb-store/src/persist.rs)` must not call commons `row_codec`.
- Move `[SharedTableRow](../../backend/crates/kalamdb-tables/src/shared_tables/shared_table_store.rs)` into commons (serialization plan Phase 2 item 5).
- Replace `batch_encode_user_table_rows` / `batch_encode_shared_table_rows` with `[ObjectEncoder](../../backend/crates/kalamdb-serialization/src/lib.rs)`. Callers: `[user_table_provider.rs](../../backend/crates/kalamdb-tables/src/user_tables/user_table_provider.rs)`, `[shared_table_provider.rs](../../backend/crates/kalamdb-tables/src/shared_tables/shared_table_provider.rs)`.

**System catalog / topics / Raft / vector:** stay on the generic object or protocol profile (`encode_object` / `encode_protocol`). Not the row profile.

## Shared rules

1. **One persistence codec.** Callers never choose FlatBuffers/FlexBuffers/JSON for RocksDB objects. Functions, indexes, topics, Raft durable payloads, and system catalog use `kalamdb-serialization`. Do not add a second codec in functions or indexes.
2. **One type system.** `CREATE TYPE`, table row types, and procedure signatures are SQL contracts. Arrow/DataFusion is the in-memory model. SDKs project; they do not define a parallel schema.
3. **One indexing core.** Scalar USER/SHARED indexes extend `IndexDefinition` / `IndexedEntityStore`. Vector hot PK uses that core. Do not add a functions- or RLS-specific index runtime.
4. **One CLI schema surface.** `kalam-schema-diff` must emit `CREATE TYPE`, `CREATE INDEX`, and `CREATE PROCEDURE` from local SQL. Generation and deploy compile local files; they do not require a live server to know the contract.
5. **Do not duplicate work.** Functions Task 3 nested serde **is** serialization Phase 2 (row `STRUCT`/`List`). Index JSON replacement **is** serialization Phase 4. Do not implement either twice.
6. **Keys are not values.** Ordered `StorageKey` bytes stay in commons. `kalamdb-serialization` does not encode RocksDB keys.

## 0.7 release gate

Ship 0.7 only when all of the following are true.

**Serialization**

- `kalamdb-serialization` is the only internal persisted-object codec crate.
- Nested `STRUCT` / named `CREATE TYPE` / `List` round-trip without JSON intermediates or `ScalarTag::Fallback`.
- Direct FlatBuffers/FlexBuffers usage outside that crate is CI-blocked (after the report-only period).
- Row **values** are ordinal KOBJ and do not repeat StorageKey fields (`user_id` / `_seq`).
- RocksDB **keys** remain today’s storekey / SeqId encoding.
- Index values are no longer stored as JSON. Definition of done in the serialization plan otherwise holds.

**Scalar secondary indexes**

- USER/SHARED tables honor catalog scalar indexes on hot seek and on flush/compaction prune.
- `CREATE INDEX` / `DROP INDEX` parse, persist on `system.schemas`, and round-trip through `kalam-schema-diff`.
- RLS membership bind prefix-scans an indexed principal column.
- Chat realtime bench no longer full-scans `messages` / `conversation_members` for the documented equality filters.

**Functions V1**

- Functions plan final release gate holds: local `ContractSnapshot`, typed `CALL`, nested calls/context, transactional topics, durable triggers, CLI deploy/dev.
- Procedure and topic payloads use the shared codec; there is no functions-only serializer.

**Together**

- A representative chat schema with `CREATE TYPE`, scalar indexes, and `CREATE PROCEDURE` compiles locally, deploys, serves indexed SQL, and executes typed `CALL` / nested procedures on those types.
- Backend/CLI smoke tests and the production-like server build pass.
- No track is deferred to “right after 0.7” while still claiming 0.7 complete.
